# Task 6 platform preflight — 2026-10-22

Read-only research supporting later Task 6; no implementation or repository changes. Sources are upstream source code and official platform documentation. No device, radio, background-delivery or interoperability testing performed.

## Findings requiring a decision before implementation

1. **Charger auto-start cannot rely on a manifest power receiver.** Android explicitly uses `ACTION_POWER_CONNECTED` as its migration example: target >=26 apps must remove that implicit manifest receiver and use scheduled charging-constrained work. Runtime receivers work only while their registered process/context survives. Charging-constrained work does not mean a fresh plug-in event and is not an exact 60-second timer. Therefore a manifest-only implementation would silently fail the brief's background promise. [Android background execution limits](https://developer.android.com/about/versions/oreo/background)
2. **A charger event does not grant permission to launch a foreground service.** For target >=31, background FGS launches require an exemption; power-connected is absent from the exemption list. Posting a countdown notification alone is not user interaction. Any existing coordinator/FGS start must be evaluated at execution time; do not assume that a delayed callback or worker supplies an exemption. [FGS background restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
3. **Current stable Health Connect conflicts with existing build settings and “add client only” ownership.** Read local `nocturne-hardening/app/build.gradle.kts`: compileSdk 35, minSdk 31, targetSdk 35; `gradle/libs.versions.toml`: AGP 8.7.3. Official setup now says connect-client >=1.1.0 needs compileSdk 36 and AGP >=8.9.1; release notes identify 1.1.0 as stable (latest alpha 1.2.0-alpha06). A modern dependency requires a coordinated build-tool change or an explicitly verified older dependency. No older artifact's AAR metadata was fetched, so none is certified here. Raising compileSdk does not inherently require raising targetSdk. [Setup](https://developer.android.com/health-and-fitness/health-connect/get-started), [releases](https://developer.android.com/jetpack/androidx/releases/health-connect)

## Lull pinned protocol: confirmed, with important qualifications

Commit `7214216` resolves to **721421664f45752ba23ff131f9f53cee589a0d90** (release 1.1 merge). Exact source: [BedJetKit/Sources/BedJetKit/BLELink.swift](https://github.com/rkanjani/lull/blob/721421664f45752ba23ff131f9f53cee589a0d90/BedJetKit/Sources/BedJetKit/BLELink.swift), blob `e8cdc1524ddec24dc4f0a5f98a25e19db27b02b8`.

- `handoffUUID(forDeviceNamed:)`: SHA-256 of UTF-8 `lull.handoff.` followed by name, first **16 bytes** (not inclusive range 0..16), byte 6 `(b & 0x0f) | 0x50`, byte 8 `(b & 0x3f) | 0x80`, raw bytes passed to `CBUUID(data:)`. It is not standard UUID-v5 SHA-1 derivation despite setting version 5. Independent Python hashlib/uuid calculation for exact name `BedJet`: `d5b6556e-0ecd-5e62-a239-403065aee3f7` (calculated fixture, not an upstream test or hardware result).
- `advertise(_:)` supplies only `CBAdvertisementDataServiceUUIDsKey: [request]`; no service-data, manufacturer-data, local-name payload or handshake. Android must advertise the derived UUID as a service UUID, and scan/filter service UUIDs, not service data. `watchForRequests()` scans `[request]` while `.ready`; `didDiscover` also checks the received service-UUID list contains the expected UUID.
- Name is **the BedJet's GATT name**, persisted under `BedJetKit.deviceName`, not phone name, MAC, profile label or scan display name. For BedJet 3 it reads characteristic `00002001-BED0-0080-AA55-4265644A6574`. [Codec.swift](https://github.com/rkanjani/lull/blob/721421664f45752ba23ff131f9f53cee589a0d90/BedJetKit/Sources/BedJetKit/Codec.swift) `parseText` decodes bytes up to first NUL as UTF-8. No trim, case-fold or normalisation occurs in derivation. Unknown name disables requests/watch. Duplicate device names produce identical requests; renamed/stale names mismatch. These are consequences of the source algorithm.
- `requestDuration = 8` seconds; requests stop early on `.ready`. `courtesy = 10` seconds, after which the yielding phone quietly attempts reconnection. An explicit `requestControl()` cancels yielded state. `connectPatience = 12` seconds. No acknowledgement/shared state is exchanged.
- `handOver(attempt:)` requires `.ready` and `canYield()`, no `pendingWrite`, no `pendingRead`; busy operations retry every 300 ms up to 15 times, then resume watching. Immediate disconnect on any observed UUID omits this transaction guard. Nocturne must avoid releasing during coordinator writes; its explicit manual suspension-until-Take-back may intentionally differ from Lull's timed courtesy, but should not be described as identical semantics.
- Android permission claim is correct for minSdk31: scanning needs runtime `BLUETOOTH_SCAN`; advertising adds runtime `BLUETOOTH_ADVERTISE`. Existing connection/GATT operations still need `BLUETOOTH_CONNECT`. `neverForLocation` is appropriate only when true, and Android warns it filters some beacons. Permission availability is not proof of radio support or delivery. [Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)
- **Cross-platform limitation:** Apple's documented background peripheral advertising moves service UUIDs into an overflow area discoverable only by iOS devices explicitly scanning for them. Thus ordinary Android service-UUID scanning cannot be promised to see a background iOS request. Foreground Lull request interop remains a hardware acceptance item. [Apple background processing](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html)

## Health Connect exact integration requirements

- Minimum data permission: manifest `android.permission.health.READ_SLEEP` and runtime `HealthPermission.getReadPermission(SleepSessionRecord::class)` only. Sleep stages are contained in `SleepSessionRecord`; heart-rate/body-sensor/write permissions are unnecessary. Check `getGrantedPermissions()` before reads and handle revocation during calls. [Sleep sessions](https://developer.android.com/health-and-fitness/health-connect/features/sleep-sessions)
- API31–33 uses separate provider `com.google.android.apps.healthdata` (declare package in `<queries>`); API34+ uses platform module. Gate creation on `HealthConnectClient.getSdkStatus()`, distinguish `SDK_UNAVAILABLE`, `SDK_UNAVAILABLE_PROVIDER_UPDATE_REQUIRED`, `SDK_AVAILABLE`.
- Rationale activity: exported handler for `androidx.health.ACTION_SHOW_PERMISSIONS_RATIONALE`; API34+ exported activity alias targeting it, protected by `android.permission.START_VIEW_PERMISSION_USAGE`, action `android.intent.action.VIEW_PERMISSION_USAGE`, category `android.intent.category.HEALTH_PERMISSIONS`. Display actual privacy/data-use policy. [Setup and rationale](https://developer.android.com/health-and-fitness/health-connect/get-started)
- Foreground History reads fit minimum permissions. Background reads and older history require additional permissions; ordinary read access reaches only 30 days before first permission grant. Do not interpret unavailable historical records as no sleep. [Read restrictions](https://developer.android.com/health-and-fitness/health-connect/read-data)
- Records/stages use instants; start/end zone offsets are nullable. Match by interval overlap and preserve the night's stored zone; the offset is not an IANA zone identifier. Missing stages do not mean awake. [SleepSessionRecord API](https://developer.android.com/reference/kotlin/androidx/health/connect/client/records/SleepSessionRecord)

## Follow-up ruling: bounded charger job, no permanent service

**Recommended amendment (engineering inference from the sources below):** F04 should mean “best-effort start while charging in the bedtime window”, not “start on the exact power-connected edge”. Use native `JobScheduler` with a charging constraint and a bounded `JobService`-owned coordinator operation. This is the smallest dependency change: the inspected Gradle files contain no WorkManager, and Task 6 permits only adding the Health Connect client. Do not add a manifest `ACTION_POWER_CONNECTED` receiver.

| Choice | Concrete fit and trade-off |
|---|---|
| Native JobScheduler | No new library. One persisted periodic eligibility job (minimum 15 min; actual cadence is inexact) is the simplest recurrence, checking the current bedtime window before radio work. A per-night one-shot with `setMinimumLatency` reduces outside-window wakes but requires explicit next-night rearming and reboot/time-change rescheduling. Both can miss the whole window. Neither detects a fresh plug-in edge. |
| WorkManager | Ordinary `CoroutineWorker` plus `RequiresCharging` is supported for short background BLE and provides persistence, unique-work/retry helpers and cancellation. It adds a dependency and still uses system scheduling: no stronger exactness. Do not call `setForeground` merely to perform this brief action; that selects long-running FGS-backed execution and its restrictions. |

[WorkRequest constraints/timing](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work) documents the 15-minute minimum, inexact periodic execution and constraint-driven delays/skips. [Long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running) documents foreground-service promotion. [JobInfo.Builder](https://developer.android.com/reference/android/app/job/JobInfo.Builder) specifies `setRequiresCharging(true)` (charging is stricter than simply plugged in), `setPersisted(true)`/`RECEIVE_BOOT_COMPLETED`, and minimum-latency semantics. Do **not** use `setOverrideDeadline` as a bedtime expiry: it relaxes functional constraints after expiry, can run beyond the requested deadline, and is not a scheduling guarantee. Check the hard window using the injected clock inside the operation.

**Ordinary job BLE is permitted without FGS.** Android's [BLE background guide](https://developer.android.com/develop/connectivity/bluetooth/ble/background) explicitly allows background connection, recommends workers/jobs for short communication, and warns process death closes the connection. The supported route is connect → bounded status/plan write/confirmation → disconnect under the running job, not starting an FGS from it or retaining a permanent connection. This proves API viability, not completion reliability.

**Lifecycle contract for Task 4/6 (proposed implementation requirements):**

- `JobService.onStartJob` returns promptly with `true`; the job owns one cancellable coroutine and BLE/session lease through countdown and operation. Protect service with `android.permission.BIND_JOB_SERVICE`. Normal terminal paths call `jobFinished` once. `onStopJob` cancels all owned work promptly; do not later call `jobFinished` for that stopped generation. Android supplies a wakelock only for active job lifetime; callbacks run on the main thread. [JobService reference](https://developer.android.com/reference/android/app/job/JobService)
- Recheck all F04 gates before showing countdown and immediately before submission, including current window, selected device, charging, notification availability, cancellation, active/manual/unknown/takeover state and minimum plan duration. Countdown starts when the job actually executes; 60 seconds is a cancellable minimum grace, not a plug-in delivery SLA. If the process/job stops, abandon that countdown; a later eligible attempt must show a fresh countdown, subject to the per-night suppression policy.
- Use an explicit short operation timeout (proposed: 120 seconds after the 60-second grace, to be validated against existing transport limits), cancellation propagated to the coordinator, finite connect timeout and deterministic session release in `finally`. Do not launch detached/global work or silently convert to FGS. A user cancel/disable must be durable before cancelling scheduled/running work.
- The coordinator's persisted per-night attempt/idempotency record must survive process death. Stop/timeout after any possibly accepted device command is an **unknown** outcome requiring reconciliation; do not automatically replay a complete upload/start. Do not claim atomic rollback of partial slot writes. Platform stop can interrupt even a correct operation; this is separate from deferrable peer hand-over.

### `canYield` across serialized slot writes

Pinned [Lull/AppModel.swift](https://github.com/rkanjani/lull/blob/721421664f45752ba23ff131f9f53cee589a0d90/Lull/AppModel.swift), line 118, installs `canYield = { [weak self] in self?.isBusy != true }` with the explicit purpose of preventing release midway through schedule saving. `BLELink` additionally tests pending read/write callbacks and retries the hand-over for at most about 4.5 seconds. **Per-packet serialization alone is insufficient:** there are callback-free gaps between the delete/write/readback/start commands of one transaction. Nocturne's peer-yield gate must remain false across the entire coordinator transaction, and the decision to release must share its serialization/ownership boundary so a new write cannot start after a stale idle check. At a safe terminal boundary it may yield; when still busy beyond the request window it may decline and resume scanning. Advertising does not entitle the requester to interrupt an upload or guarantee release. Explicit stop/process death still needs the coordinator's unknown-result handling rather than waiting indefinitely for a “safe” transaction boundary.
