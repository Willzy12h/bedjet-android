#### Important (Should Fix)

**I1 — Stop callbacks compare parcelled parameters by object identity, leaving work running after Android stops the job.**

- **Location:** `app/src/main/kotlin/io/github/willzy12h/nocturne/platform/ChargerJobs.kt:94–96`; ownership and terminal cleanup at `:69–91`.
- **Evidence:** `running?.takeIf { it.params === params }` only cancels when the stop callback receives the exact in-memory object passed to start. Android delivers start and stop through separate Binder calls with `in JobParameters` and JobServiceEngine forwards each incoming object to its corresponding main-thread callback; it does not look up and reuse the start object. Therefore reference equality is not the job identity. Source basis: [AOSP IJobService AIDL](https://android.googlesource.com/platform/frameworks/base/%2B/android10-release/core/java/android/app/job/IJobService.aidl), `startJob`/`stopJob`; [AOSP Android34 JobServiceEngine](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/%2B/refs/heads/androidx-datastore-release/android-34/android/app/job/JobServiceEngine.java), `JobInterface.startJob`, `stopJob`, and `JobHandler` execute/stop cases. These were retrieved in the focused source check. Distinct Binder unmarshalling plus direct forwarding explains the mismatch; this is not a hardware finding.
- **User impact:** A stopped countdown can keep running, or a hardware transaction can continue after constraint loss, cancellation or scheduler preemption. Rechecking eligibility does not solve preemption while charging remains true, and no eligibility check interrupts a transaction already underway. The finally block can then call `jobFinished` for an execution Android already stopped because `owner.stopped` was never set. Service destruction may eventually cancel the work, but onStopJob must itself honour the contract.
- **Fix:** Match the active job by supported logical identity (this dedicated service owns only the reserved job ID), mark that running owner stopped, and cancel its owning coroutine promptly. Keep the local Running-generation identity guard for asynchronous cleanup. Do not simply clear `running` and permit a replacement execution while old cleanup can still cancel the shared notification or finish the wrong generation. Start/stop callbacks are main-thread ordered; ensure an old coroutine's completion never clears/cancels a newer owner. If supporting overlapping/delayed generations beyond the framework callback ordering, introduce an explicit generation mechanism rather than assuming JobParameters object identity is one.
- **Focused regression required:** Start an injected suspending owned operation, then invoke onStopJob with a distinct JobParameters instance representing the same ID. Assert cancellation reaches grace and, separately, in-flight owned work; stopped execution must not call jobFinished. Exercise a later execution and delayed old cleanup to ensure the new owner/notification is preserved and a fresh grace is required. The existing `ChargerRunTest.stoppedGraceDoesNotSurviveAndNextAttemptGetsFreshGrace` cancels the runner directly and never exercises this adapter boundary.

**I2 — Exported text can become executable spreadsheet formulas.**

- **Location:** `app/src/main/kotlin/io/github/willzy12h/nocturne/platform/HistoryCsv.kt:12–16,29–35`.
- **Evidence:** The encoder only redacts address-shaped substrings and applies CSV syntax escaping. `n.profileName` and `n.id` are emitted as raw cell values. For a profile name `=1+1`, the profile cell is exactly `=1+1`; a formula containing commas is double-quoted but remains a formula cell after CSV parsing. Imported/user-authored text reaches this export. Event detail currently has an enum prefix, which makes a marker at the start of its detail non-leading; the confirmed example is the profile/name or another raw free-text cell, not an assertion that every event detail directly executes.
- **User impact and calibration:** Opening a history CSV in a spreadsheet can evaluate imported text as formulas; depending on the spreadsheet and settings this can misrepresent data or invoke external-content behaviour. Exploitation requires importing/using crafted text and opening the resulting export in a spreadsheet. No execution, exfiltration or remote-code exploit was demonstrated. This is Important, not Critical. RFC4180 compliance does not prevent it. [OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection) documents the distinction and the limits of mitigation across spreadsheet applications.
- **Fix:** Define a spreadsheet-safe text-cell policy before RFC escaping, covering formula-leading characters and control/whitespace prefixes in untrusted textual columns while leaving generated numeric columns numeric. A visible inert prefix is a simple conservative option; spreadsheet-specific apostrophe/tab conventions require an explicit supported-consumer choice and must not be advertised as universal protection. Document any changed raw text representation. Add focused tests for `=1+1`, `+`, `-`, `@`, leading tab/CR/LF, quotes and separators in profile/other exported text, with identifiers both enabled and disabled. Verify cells parse as inert text under the selected export policy.
